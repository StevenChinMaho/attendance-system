# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

國中校園點名系統 (a junior-high-school attendance system). Full business context, permission model, and database ERD live in [system_structure.md](system_structure.md) — read it before touching schema, roles, or attendance business logic. All functional phases are implemented: accounts/roles, school classes/students/teachers, attendance recording (`attendance_sessions`/`attendance_records`), the follow-up/audit-log domain (`attendance_follow_ups`, activitylog integration), and the live status dashboard (`App\Livewire\Attendance\StatusBoard`, polling-based). Only production deployment (see system_structure.md's 開發流程規劃) remains.

## Commands

This project is developed exclusively through **Laravel Sail**. Do not run bare `composer`/`php artisan`/`npm` on the host — host PHP/Node versions are not guaranteed to match the container, and the project's dev guideline requires Sail.

```bash
./vendor/bin/sail up -d                                        # start containers (app + mariadb)
./vendor/bin/sail artisan migrate --seed                       # run migrations + seed
./vendor/bin/sail artisan test                                 # full test suite
./vendor/bin/sail artisan test --filter=test_method_name        # single test
./vendor/bin/sail artisan test tests/Feature/ExampleTest.php    # single file
./vendor/bin/sail artisan pint                                  # code style fix
./vendor/bin/sail artisan tinker
./vendor/bin/sail npm run dev                                   # Vite dev server
./vendor/bin/sail npm run build                                 # production assets
```

The `composer.json` `dev` script (`composer run dev`) invokes bare `php artisan serve`/`npm run dev` outside any container — don't use it; it's a leftover from the Laravel skeleton and bypasses Sail.

`migrate:fresh --seed`/`migrate --seed` restores more than just roles/permissions and the admin account: `DatabaseSeeder` also calls `Database\Seeders\DemoDataSeeder` (guarded to `local`/`testing` environments only) to recreate a fixed, predictable set of manual-testing data — two classes in the *current* academic year/semester, each with a homeroom teacher (`teacher1`/`teacher2`), plus two student-role accounts (`rep1`/`rep2`), all passwords `password`. This exists so wiping the dev database for a clean-slate test doesn't cost a round of manually recreating classes/teachers/accounts through the UI every time — if you add more seed-worthy demo data, extend `DemoDataSeeder` rather than hand-creating it once and losing it on the next `migrate:fresh`.
  - **It deliberately seeds zero students, and the classes come up empty.** Students now have a real bulk-loading path (`/admin/students/import`, fed by the school's own whole-school Excel export), so an empty class is the correct starting point for exercising that flow — pre-seeded fake students would just have to be cleared first every time. The consequence to know about: `rep1`/`rep2` exist but link to no `Student`, so `User::ownSchoolClasses()` is empty for them, the nav bar shows no 點名 entry, and `/attendance` bounces them to the dashboard. To manually test attendance as a student, first create/import students, then link one of those accounts from 學生管理.

## Architecture

**Auth is username-based, not email-based.** The `users` table (see `database/migrations/0001_01_01_000000_create_users_table.php`) has no `email` column and no `password_reset_tokens` table — there is no self-service registration or password-reset flow by design (accounts are provisioned by an admin; a disabled account must be reset by an admin manually). `App\Models\User` casts `is_active`/`last_login_at` and uses spatie's `HasRoles` trait for role/permission checks.

**Identity is split into two layers, deliberately:**
- *Login identity* (`users` table + spatie roles/permissions) answers "can this account do X at all."
- *Business identity* (`students`/`teachers` tables) answers "which real person/class does this account represent." A `User` optionally links to at most one `Student` (only students who need to log in themselves have accounts) or one `Teacher` via a nullable, unique `user_id` FK on the child table — most students/teachers have no linked account. `App\Rules\UserAccountIsUnlinked` enforces at the validation layer that one account can never be linked to both a student and a teacher; `User::ownSchoolClasses()` is the single place that resolves "which classes does this account belong to" — both a student and a teacher can now have several (`Student::schoolClasses()`/`Teacher::homeroomClasses()` are both effectively-`hasMany`-shaped: see the `school_class_student` paragraph below for why a student, like a teacher, is no longer capped at exactly one class). `User::ownSchoolClass()` is a thin wrapper returning `ownSchoolClasses()->first()` (most recent by academic year/semester) for call sites that only need a single default target (e.g. `GoToMyClassAttendanceController`'s redirect) — reuse these rather than re-deriving the relation inline.
- Row-level scoping (e.g. "only for my own class") is **not** something spatie/laravel-permission handles — it only answers the role/permission question. Scoping is implemented in Laravel Policies (see `App\Policies\SchoolClassPolicy::recordAttendance`, wired onto `SchoolClass` via the `#[UsePolicy]` attribute) that check `$user->ownSchoolClasses()->contains('id', ...)` against the target resource — **membership in the full collection, not equality against `ownSchoolClass()`'s single "most recent" pick**, specifically so a teacher with more than one homeroom (concurrent or past) can manage all of them, not just whichever one `ownSchoolClass()` happens to return. The nav bar (`resources/views/components/nav-bar.blade.php`) mirrors this: it renders a plain "點名" link only when `ownSchoolClasses()->count() === 1`, otherwise a `<select>` listing every class the account holds.

**Livewire components are not re-authorized by route middleware after the initial page load — this is the single most important gotcha in this codebase.** Route middleware (`auth`, `can:...`) only runs on the first full-page request. Subsequent `wire:click`/`wire:model` interactions hit Livewire's own `/livewire/update` endpoint, which Livewire re-applies only a small hardcoded allowlist of middleware to (`Illuminate\Auth\Middleware\Authenticate`/`Authorize`, `SubstituteBindings`, a few others — see `Livewire\Mechanisms\PersistentMiddleware\PersistentMiddleware::$persistentMiddleware`). Custom middleware like `EnsureAccountIsActive` and package middleware like spatie's `role`/`permission` are **not** in that list and silently do not get re-checked on interactions — this is exactly why all five `Admin\*Manager` routes deliberately use Laravel's own `can:permission-name` (which resolves to `Illuminate\Auth\Middleware\Authorize`, one of the allowlisted classes) instead of spatie's `role:...`/`permission:...` middleware: it's the one route-level guard in this codebase that actually *does* get reapplied on every Livewire interaction, not just the first load. `Livewire::test()` makes all of this worse to catch: it never exercises `PersistentMiddleware` at all (it explicitly skips "fake requests such as a test"), so a component can look fully protected in tests while being wide open to a mid-session role/permission change in production — including the `can:` middleware case above, since the test harness never dispatches through it either.
  - The fix used throughout this codebase: authorize *inside the component*, in a hook that reruns on every request, not just `mount()` (which only runs once). Use `boot()` for a single component (see `App\Livewire\Attendance\Recorder::boot()`, guarded with `isset($this->schoolClass)` since `boot()` fires *before* `mount()`'s own body on the very first load) or a trait with a `boot{TraitName}()` method for a check shared across components (see `App\Livewire\Concerns\RequiresPermission`, used by all five `Admin\*Manager` components). Both hooks fire on `mount()` **and** every subsequent `hydrate()` (i.e. every interaction), and — unlike route middleware persistence — they *do* run under `Livewire::test()`, so they're actually covered by the test suite. Keep this component-level check even where the route middleware happens to be persistent (see `can:` above) — it's the only layer `Livewire::test()` ever exercises, and it doesn't rely on an implementation detail of which middleware classes Livewire's allowlist happens to include.
  - A public Livewire array property (e.g. `Recorder::$statuses`, keyed by `student_id`) is also client-writable on every update request — validating only the *values* isn't enough. `Recorder::submit()` builds its write set by iterating the server-derived roster (`$this->students()`) and looking up each student's status from `$statuses`, rather than iterating `$statuses`' own keys, specifically to stop an extra injected key (a student id from another class) from being written.

**A nested `<livewire:...>` component keyed only by a record's ID goes stale when the parent re-renders with updated data for that same record — this cost real debugging time once already, don't repeat it.** Livewire treats a nested component matched by an unchanged `wire:key` as "the same already-mounted child" and does not force it to re-mount/re-fetch just because the parent recomputed the model passed into it; the child only refreshes when *its own* actions fire. Concretely: `resources/views/livewire/attendance/recorder.blade.php` keys `<livewire:attendance.follow-up-manager>` as `'follow-up-'.$record->id.'-'.$record->status->value` (not just the id) specifically so correcting a status forces the child to remount and reflect the record's current follow-ups — with only the id in the key, the exact same markup renders and the debug values in the parent's Blade context are correct, but the mounted child silently keeps showing what it showed when it was first mounted. If a future nested component depends on data that can change without the parent's own key inputs changing, extend the key (or find another explicit refresh path) rather than assuming a parent re-render is enough.

**`spatie/laravel-activitylog`'s `LogsActivity` trait lives at `Spatie\Activitylog\Models\Concerns\LogsActivity` in the installed version**, not the `Spatie\Activitylog\Traits\LogsActivity` path shown in older docs/tutorials (same for `LogOptions`, at `Spatie\Activitylog\Support\LogOptions`) — get the import wrong and it's a "trait not found" error, not a subtler bug. Separately: `AttendanceRecord::upsert()` in `Recorder::submit()` is a bulk query-builder write and does **not** fire Eloquent's `saving`/`saved` events, so `LogsActivity`'s automatic dirty-attribute logging never triggers for it — the audit trail for status changes is written manually instead (`Recorder::logStatusChanges()`, using the `activity()` helper directly, wrapped together with the upsert in one `DB::transaction()` with `lockForUpdate()` on the "previous state" read so a corrected status and its audit entry can't diverge under concurrent submits). If you add another bulk-write path against an audited model, it needs the same manual-logging treatment — the trait alone won't catch it.

**All audit writes go through `App\Support\AuditLog` — never call `activity()` directly.** It's a plain final class (same trait-constant reason as `AcademicPeriod`/`AttendanceWindow`/`ClassCode`) owning the `log_name` constants (`auth`, `admin`, `attendance_session`, `attendance_record`, `attendance_follow_up`) and three conventions that a future query UI depends on: descriptions are always Chinese (spatie's automatic logging on `AttendanceFollowUp` still emits `created`/`updated`/`deleted`, which is the one exception); **`properties` carries a human-readable snapshot, not just ids** (class label, student name/number, username) so a log line stays meaningful after the row it references is renamed or deleted — the value deliberately means "what it was at the time", which is the point of an audit trail; and **no password value is ever logged, hashed or not** (`AuditLogTest` asserts this across every path).
  - **`Recorder::logSubmission()` exists because `logStatusChanges()` deliberately skips "first entry + present".** That skip means a submitted roster where *everyone is present* produced **zero** audit rows — precisely the case that matters if someone uses a borrowed account to fire off a blank all-present sheet. `attendance_sessions.recorded_by` doesn't cover it either: `firstOrCreate` only sets it on creation, so it records the *first* person to take that session and never updates on re-submit. The session-level entry logs every submit (`點名單送出` / `點名單重新送出`) with a per-status count summary, so the log answers "what was submitted" without joining anything.
  - **Failed logins only record the attempted username when that account actually exists** (`LoginController::loggableUsername()`). Typing a password into the username field is a common slip, and that string would otherwise sit in plain text in a log admins can read; an unknown username still logs the IP and timestamp, so "someone is probing" remains visible. Every auth entry carries `ip`/`user_agent`, which is only meaningful because `trustProxies` is configured — without it every row would read as the nginx container's internal IP.

**Routing/auth middleware is applied per route group in `routes/web.php`**, not globally in `bootstrap/app.php`. New route groups must explicitly wrap protected routes in `Route::middleware('auth')`; the login page (`/`) is the only route under `guest` middleware and must stay the only thing an unauthenticated visitor can reach. `GET /login` is also registered (same `LoginController::create()`, same `guest` middleware) purely as an alias so a manually-typed `/login` URL doesn't 405 — `/` stays the one *named* `login` route everything else references.

**`LoginController::store()` rate-limits by `RateLimiter` keyed on `lowercase(username)|ip`** (5 attempts / 60s, cleared on success) — this is the app's only defense against password brute-forcing, since accounts have no other lockout mechanism (`is_active` is admin-toggled, not automatic). Hitting the limiter happens on *every* rejection path (wrong password, disabled account) before revealing which one it was, so the limiter itself doesn't leak whether a username exists. If you touch `store()`, keep the `RateLimiter::hit()` calls on both failure branches — losing one re-opens unlimited guessing against that specific failure mode.

**Database:** MariaDB via the dedicated `mariadb` Laravel connection (`DB_CONNECTION=mariadb` in `.env`), not the `mysql` driver — `config/database.php` already ships both. `spatie/laravel-permission` and `spatie/laravel-activitylog` migrations have already been published into `database/migrations/` (`create_permission_tables.php`, `create_activity_log_table.php`) — don't re-publish them.

**Frontend:** Blade + Livewire 4 + Tailwind CSS 4 (via `@tailwindcss/vite`). No SPA/API layer — Sanctum is not installed. The shared layout is an anonymous Blade component at `resources/views/components/layouts/app.blade.php` (`<x-layouts.app>`), which already includes `@livewireStyles`/`@livewireScripts`.

**Shared visual design lives in `resources/css/app.css` as reusable component classes (`.btn-primary`, `.field-input`, `.data-table`, `.surface`, `.badge-*`, `.alert-*`, `.action-group`, …), not repeated per-file utility strings.** Blade views compose these (e.g. `class="btn-primary"` instead of spelling out `rounded-md bg-indigo-600 px-3 py-1.5 ...` inline) so a style change (spacing, colors, dark-mode pairing) is made once and takes effect everywhere. **Tailwind v4's `@apply` can only reference real utilities, not another custom class defined via `@apply`** — `.btn-primary`/`.btn-secondary`/etc. all need to layer on top of a shared `.btn` base, so `btn`/`badge` are declared via the `@utility` at-rule (top-level, alongside `@theme`, plain CSS properties — not `@layer components`) specifically so later `@layer components` rules can legally `@apply btn ...`; get this backwards (`.btn` as a plain `@layer components` class that others `@apply btn` from) and the Vite build fails with "Cannot apply unknown utility class". **Dark mode is class-based, not `prefers-color-scheme`-based**, via `@custom-variant dark (&:where(.dark, .dark *));` in `app.css` — so `dark:` utilities only activate when `<html>` carries a `.dark` class, toggled by `resources/views/components/theme-toggle.blade.php` (Alpine — bundled with Livewire's `@livewireScripts`, no separate install) and persisted to `localStorage`. The layout's `<head>` runs a synchronous inline script *before* `@vite` loads to set `.dark` from `localStorage` (falling back to `prefers-color-scheme` only when nothing is stored yet) — this has to run before first paint or the page flashes the wrong theme.
  - **`.data-table-uniform-rows` (opt-in, currently only `RoleManager`) exists because a table where only *some* rows carry a button gets visibly ragged row heights.** In `/admin/roles` the three built-in roles have their permissions locked and therefore render no 刪除 button, while custom roles do — and `.btn-xs` (1.5rem) is taller than the plain text next to it, so the first three rows sat noticeably shorter. The rule sets `height: 2.5rem` on `td` (cell `py-2` = 1rem, plus that 1.5rem button), which in table layout behaves as a *minimum* — taller content still expands the row rather than being clipped.

**Attendance status is a native PHP backed enum** (`App\Enums\AttendanceStatus`, values like `PRESENT`/`LATE`/`ABSENT`), cast on `AttendanceRecord::status` — not a DB-level enum column, so adding a status only touches the enum class. **`attendance_sessions.period` is deliberately a plain string, not an enum** (currently only `MORNING`/`NOON`/`AFTERNOON` are valid, enforced at the application layer in `App\Livewire\Concerns\AttendancePeriods::PERIODS`) — this is intentional flexibility for a possible future move to per-period attendance without a schema change; don't "fix" it into a stricter type without checking system_structure.md's rationale first. `attendance_sessions` existing for a given `(school_class_id, date, period)` *is* the "attendance was taken" signal — there's no separate submitted/draft flag. `Recorder` and `StatusBoard` both depend on `AttendancePeriods` for the period list/labels and "what's the current period right now" logic — it's a plain final class, not a trait, specifically because **PHP does not allow accessing a trait's constants from outside a class that `use`s it** (`SomeTrait::CONST` from a Blade view or another class fails at compile time) — this was tried and reverted once already, don't redo it as a trait.

**Cross-cutting query/authorization patterns live in small `Concerns` traits/classes, reused rather than copy-pasted per model or component** — check there before adding a new one: `App\Models\Concerns\HasNaturalStringSort` (the `LENGTH(col) asc, col asc` trick `Student::scopeOrderBySeatNumber()` delegates to, since `seat_number` is a string kept flexible for non-numeric codes but needs numeric-ish sort order); `App\Livewire\Concerns\RequiresPermission` (the `bootRequiresPermission()` per-request re-auth used by all five `Admin\*Manager` components — each declares its own `protected string $requiredPermission`, checked against the account's spatie permissions, not a hardcoded role name); `App\Livewire\Concerns\ScopesToSelectedAcademicPeriod` (the `bootScopesToSelectedAcademicPeriod()` used by `SchoolClassManager` and `StatusBoard` to filter by the session-stored "currently selected" academic year/semester — see next paragraph); `App\Livewire\Concerns\SortsColumns` (click-to-sort table headers, used by `UserManager`/`TeacherManager` — see below).

**`SortsColumns`' whitelist is a security boundary, not a convenience.** `$sortColumn`/`$sortDirection` are public Livewire properties, so they are client-writable on every update request (same class of problem as `Recorder::$statuses`) — interpolating either into `orderBy()` is SQL injection. Every component declares `sortableColumns()` mapping a display key to either a column name or a `Closure(Builder, string $direction)`, plus a `defaultSortColumn()`; `activeSortColumn()` falls back to the default whenever `$sortColumn` isn't a whitelist key, and `activeSortDirection()` only ever returns `asc`/`desc`. Blade reads the same two accessors the query does, so the triangles can't disagree with the actual ordering. `UserManagerFilteringTest`/`TeacherManagerFilteringTest` pin the fallback behaviour with injection-shaped values.
  - **Sorting a column whose displayed value isn't a plain DB column must mirror the display logic, or rows look "unsorted".** `TeacherManager`'s 姓名 column renders `displayName()` (the linked account's name when there is one, else `teachers.teacher_name`), so it sorts by `COALESCE(users.name, teachers.teacher_name)` over a **`leftJoin`** — left, so teachers without an account don't vanish, and with an explicit `select('teachers.*')` so the joined `users.id`/`users.name` don't overwrite the model's own attributes.
  - **A search that ORs several columns must wrap them in a nested `where(fn ($q) => ...)`.** Without the closure the `orWhere`s flatten into the same level as the other filters and the dropdown filters silently stop narrowing anything — it reads as "the filter doesn't work" rather than as a query bug. `StudentManagerFilteringTest::test_search_and_filter_are_combined_with_and_not_or` exists for exactly this.
  - Filter properties get `updated{Property}()` hooks calling `resetPage()` — otherwise a user sitting on page 5 of the old result set sees a blank table under the new one. `StudentManager` additionally resets `classFilter` on `academic-period-changed`, since a class from the old period matches nothing in the new one.

**The pagination bar is a project-owned view at `resources/views/vendor/livewire/tailwind.blade.php`, which overrides Livewire's built-in `livewire::tailwind` by filename.** Livewire's `SupportPagination` resolves the view as "component's `paginationView()` method, else `livewire::{theme}`", and `livewire::*` is registered with `loadViewsFrom()`, so Laravel prefers `resources/views/vendor/livewire/`. This is deliberately the *filename override* rather than a `paginationView()` method or a trait: every paginated screen then gets the same bar automatically, with nothing for a future component to remember to opt into. Three things the replacement fixes, all reported against the built-in one: it used `gray-*` while this project is `slate-*` throughout (visibly a different design system); its entire body sits inside `@if ($paginator->hasPages())`, so a single-page result rendered *nothing* — not even the record count; and it had no "page N of M" and no visibly-disabled state at either end. Styling lives in `app.css` as `.pagination-*`, and `.pagination-btn:disabled` spells out its own border/background/text for both themes for the same reason `.field-checkbox` does — browsers' default disabled rendering is nearly indistinguishable in dark mode. Note that Blade's `@disabled()` emits a *bare* `disabled` attribute, so a test asserting on it must not look for `disabled="disabled"` (and must not be fooled by the `wire:loading.attr="disabled"` on the same button).

**The academic-year/semester filter is global, session-backed, and broadcast across independently-mounted Livewire components via a dispatched event — not a per-component property.** `App\Support\AcademicPeriod` (a plain final class, same trait-constant rationale as `AttendancePeriods` below) computes "the current academic year/semester" from today's date (year starts 8/1, semester splits at the Jan/Feb boundary) and reads/writes the user's *selected* year/semester to/from session (`AcademicPeriod::selectedYear()`/`selectedSemester()`/`setSelected()`) — this is deliberately per-browser-session state, not a `users` table column, since it's "what I'm currently looking at," not an account setting. `App\Livewire\AcademicPeriodSwitcher` (mounted once in the nav bar) is the only place that *writes* the selection; on change it calls `AcademicPeriod::setSelected()` then `$this->dispatch('academic-period-changed')` — a global Livewire browser event that any other mounted component can listen for. `SchoolClassManager` and `StatusBoard` pick this up via `ScopesToSelectedAcademicPeriod`, which declares both a `boot{TraitName}()` (rereads the session value on every request, same mechanism as `RequiresPermission`) *and* a `#[On('academic-period-changed')]` listener method — the listener body is intentionally empty; its only job is registering interest in the event so Livewire triggers a hydrate (which re-runs `boot()`) the moment the switcher fires, instead of waiting for the component's own next unrelated interaction (or, for `StatusBoard`, its next 15s poll tick). If a component needs extra work when the period changes (e.g. `SchoolClassManager::resetPageOnPeriodChange()` resetting pagination), add a second, separately-named `#[On('academic-period-changed')]` method in that component rather than putting pagination-specific logic in the shared trait — Livewire calls every method across the class (own + traits) that declares the same `#[On]` event. `GoToMyClassAttendanceController` and `App\Livewire\AttendanceQuickLink` (the nav bar's "點名" entry, shared by student_rep/homeroom_teacher/admin — see below) filter `User::ownSchoolClasses()` down to `AcademicPeriod::selectedYear()`/`selectedSemester()` too — this is a *display/redirect-target* filter only (which class is the quick-link default, which classes appear in the dropdown), not an authorization change: `SchoolClassPolicy`/`AttendanceRecordPolicy` still allow direct access to any class in the account's full `ownSchoolClasses()` list regardless of the selected period, since a teacher may still need to reach a past semester's class by URL for a correction even though it no longer appears in the quick-pick dropdown.

**Because the selected period only changes a few times a year and then sits untouched, it's easy to forget you're not looking at the actual current one — `AcademicPeriod::isSelectedCurrent()` (`selectedYear() === currentYear() && selectedSemester() === currentSemester()`) exists specifically to flag that mismatch everywhere it matters, rather than each screen separately comparing the two pairs.** `AcademicPeriodSwitcher`'s own dropdowns get a `badge-warning` "⚠ 非本學期" right next to them (not hidden behind a hover title — this needs to be seen without deliberately looking for it), and `SchoolClassManager`/`StatusBoard`'s "顯示範圍：..." subtitle recolors itself amber with a "（非本學期）" suffix for the same reason — `StatusBoard` in particular is a page people glance at repeatedly through the day, where "no sessions submitted yet" reads very differently depending on whether you're actually looking at today's semester. Reach for this helper (not a fresh `selectedYear() === currentYear() && ...` comparison) if a future screen needs the same warning, so the definition of "current" can't drift between call sites.

`Recorder` and `StatusBoard` each independently carry their own local `$date` (defaulting to `now()->toDateString()`, freely changeable to correct/inspect a past day — this is *not* session-backed shared state like the academic period, so there's no equivalent `AcademicPeriod`-style singleton to hang a helper off) — both get the same "⚠ 非本日" `badge-warning` next to their date `<input>` via a plain inline `$date !== now()->toDateString()` check, for the identical reason: switching the date is a legitimate, common action (backfilling a missed session, checking a prior day), but it's easy to forget you're not on today once you've moved on to actually filling in statuses, and a submitted correction looks identical on screen to routine same-day attendance-taking.

**`AttendanceQuickLink` is the single nav-bar "點名" entry point shared by all three roles that can take attendance** (student_rep/homeroom_teacher via `ownSchoolClasses()`, admin via *every* `SchoolClass` in the selected period, since admin has no "own" classes) — admin no longer has a separate "點名" link embedded in the `SchoolClassManager` table row; that action was removed from `school-class-manager.blade.php` specifically so there'd be exactly one place a class's attendance page is reached from, matching student_rep/homeroom_teacher. `nav-bar.blade.php` gates the `<livewire:attendance-quick-link>` tag itself with `@can('attendance.record')` (not a role check) for the same reason the admin-page links are permission-gated (see below) — a custom role holding `attendance.record` needs the nav entry to actually appear, not just the underlying route to allow it. It uses `ScopesToSelectedAcademicPeriod` for the same live-reactivity-to-the-switcher reason as `SchoolClassManager`/`StatusBoard`. **A Livewire component's rendered view must always have exactly one root HTML element, even on the branch where there's nothing to show** — an early version of this component's Blade view was a bare `@if/@elseif/@elseif` with no wrapping tag, which produces zero root elements on the "admin, no classes in this period" branch; Livewire throws `RootTagMissingFromViewException` when that happens, and because the component is embedded in the shared nav bar, the exception took down *every* authenticated page for that user, not just this component — wrap conditional-only component views in an unconditional outer `<div>`.

**`SchoolClass::label()` (with the academic year prefix, e.g. "115學年度 1年3班") vs `SchoolClass::shortLabel()` (e.g. "1年3班") — pick based on whether the surrounding screen already establishes a single academic year from context.** Since the nav bar's `AcademicPeriodSwitcher` pins one year/semester at the top of nearly every screen (and it changes only a few times a year, not per-visit), re-printing the year next to every class row/heading on an already-scoped screen (class management list, status board, the recorder's own heading, the nav bar's class picker) is pure noise — those all use `shortLabel()`. Reach for `label()` only where a screen can legitimately show classes from *different* academic years side by side with no other cue which is which (there is no such screen today, but if one is added, that's the signal to use `label()` there).

**The `Admin\*Manager` components with both a create form and an inline edit form (`SchoolClassManager`, `TeacherManager`, `StudentManager`, `ClassRosterManager`) must keep `$showCreateForm` (or equivalent) and `editing{X}Id` mutually exclusive — they used not to, and it produced a real bug.** Create and edit reuse the *same* public properties (e.g. `StudentManager::$studentNumber`) for their form fields, since it's the same entity shape either way. If both `$showCreateForm` is true and an `editing{X}Id` is set at once, Blade renders both forms and — because they're bound to the same properties — typing in one visibly changes the other, and submitting the create form silently carries whatever values `startEdit()` last populated (the record being edited's own student number/class number), which then collides with that very record's unique-constraint fields and 500s instead of showing a validation error. The fix: a `toggleCreateForm()` method (replacing the old `wire:click="$toggle('showCreateForm')"`) calls `cancelEdit()` before opening the create form, and `startEdit()` sets `$this->showCreateForm = false` before populating the edit fields — so opening one always closes the other, and the shared properties get reset (via `cancelEdit()`'s `$this->reset(...)`) rather than carrying over stale values. `UserManager` extends this to a **three-way** mutual exclusion (`showCreateForm` / `editingUserId` / `resettingPasswordUserId`) since it grew both an edit form and a separate reset-password form on top of create; `StudentManager` goes to **four** (adding `markingLeftStudentId` and `restoringStudentId` on top of create/edit — see the `StudentDeparture` paragraph above) — in both cases every `start*()`/`toggle*()` entry point cancels *all* of the other states before opening its own, not just one. `ClassRosterManager` (see the `school_class_student` paragraph below) has its own, smaller two-way version of the same pattern (`showAttachForm` / `editingSeatForStudentId`), since it shares `$seatNumber` between the "attach a new student" form and the "change an existing student's seat number" form. If a future admin manager grows both a create and an edit form sharing properties, give it the same `toggleCreateForm()`/`showCreateForm = false`-in-`startEdit()` treatment up front (extended to every additional mutually-exclusive state it grows, not just the first pair).

**Linking an account to a student starts from the *student*, not from the account — the reverse direction was the original design and it does not scale.** Creating the account at `/admin/users` and then hunting for the right student among 300+ rows (and for the right account in an unbounded `<select>`) is backwards: nobody creates a student login in the abstract and then decides who it belongs to. `StudentManager` therefore has a per-row 「建立帳號」 panel that creates the `User` (name copied from the student, username defaulting to their 學號, role fixed to `student_rep`, `must_change_password` set) **and links it in one action** — the same shape as `SchoolClassManager`'s 「+ 新增老師」 quick-add, just on the other side of the relation.
  - `linkSuggestedAccount()` clears the pre-existing backlog of unlinked accounts by offering a one-click link when an unlinked account's `users.name` exactly matches the student's. It only suggests when **exactly one** account shares that name — a school this size reliably has duplicate names, and silently picking one produces "A's account linked to B", which is both hard to notice and hard to trace afterwards. Because it is a `wire:click` target taking client-supplied arguments, it re-checks all three conditions server-side (account still unlinked, student still unlinked, names actually equal); arbitrary pairings go through the edit form instead. `createAccountForStudent()` likewise re-checks that the student has no account, since the button is only *rendered* for unlinked rows.
  - Both `StudentManager` and `TeacherManager` cap the account `<select>` at 50 rows behind an `accountSearch` filter. **The currently selected account is always prepended when the filter would exclude it** — otherwise typing in the filter drops the in-progress link out of the `<select>`, which looks like it was cleared and then really does clear it on submit.
  - `StudentManager`'s mutually-exclusive row states are now **five** (create / edit / mark-left / restore / create-account); every `start*()`/`toggle*()` must cancel the other four, per the pattern documented above.

**A `Teacher` or `Student` row's name is never independently hand-typed when it has a linked `User` account — it's always derived from that account's `users.name`, via the shared `App\Models\Concerns\HasLinkableAccountName` trait's `resolveName(?int $userId, ?string $manualName)`/`displayName()`.** This exists specifically to kill a redundant-input smell: creating a linked teacher/student used to ask the admin to type the same person's name twice (once for the account, once for `teachers.teacher_name`/`students.name`), and the two copies could drift apart with nothing to flag it. `TeacherManager::createTeacher()`/`updateTeacher()`, `StudentManager::createStudent()`/`updateStudent()`, and `SchoolClassManager::quickAddTeacher()` all funnel through `resolveName()` rather than trusting the client-submitted `teacherName`/`name` property whenever a `userId` is present — the "姓名" field in all these forms swaps from an editable input to a read-only preview of the selected account's name the moment `userId` is set (via `wire:model.live` on the account picker), so there's no UI path left for the two to diverge in the first place. `displayName()` goes a step further for *display*: it prefers `$this->user?->name` live over the stored name column whenever a link exists, falling back to the stored column only for unlinked rows — this means a future "rename this account" feature wouldn't need a matching sync migration/job, since nothing caches a stale copy for display. A model using the trait must implement `manualNameColumn()` to say which column holds the manually-typed fallback (`teacher_name` for `Teacher`, `name` for `Student` — the trait can't assume a shared column name across the two). Every `displayName()` call site must eager-load `user` (e.g. `Teacher::with('user')`, `SchoolClass::with('homeroomTeacher.user')`, `$schoolClass->students()->with('user')`) or it N+1s per row.
  - **Why `Teacher` still exists as a concept separate from `User` at all** (raised and deliberately kept, not an oversight): per system_structure.md, a homeroom teacher does not strictly need a login — some may have their attendance/follow-up work fully delegated to a student in their class who does have a login, and never touch the system themselves, yet the school still wants "who is this class's homeroom teacher" recorded. Collapsing `SchoolClass::homeroom_teacher_id` to point at `User` directly would force provisioning a username/password for every homeroom teacher merely to name them, which is strictly more admin burden, not less. `teachers.user_id` stays nullable specifically to keep that case cheap.
  - **`SchoolClassManager` embeds a "+ 新增老師" quick-create panel directly next to its homeroom-teacher `<select>`** (`showQuickAddTeacher`/`newTeacherName`/`newTeacherUserId`/`quickAddTeacher()`), so assigning a brand-new homeroom teacher to a class no longer requires a side trip to `/admin/teachers` first — the newly created `Teacher`'s id is written straight into `$homeroomTeacherId`, the same property the surrounding create-class form is already bound to. This mini-form is intentionally only on the create-class form, not the inline per-row edit form — by the time an admin is correcting an existing class, the teacher pool has typically already been built out, so the marginal value of duplicating the panel there was judged not worth the added component complexity.

**A permission is *data*, not code — adding `can:foo` to a route does nothing until `RolePermissionSeeder` has been re-run.** spatie stores permissions in the `permissions` table, so a permission that exists only in the seeder's source array is absent from any database that hasn't re-seeded: the route 403s for *everyone including admin*, and `/admin/roles` doesn't even list it as a checkbox — with no error anywhere. This was hit for real with `audit.view`. Two consequences:
  - **The production entrypoint runs `db:seed --class=RolePermissionSeeder` on every container start**, for the same reason it runs `migrate --force`: code and the data it requires must go live together, never depending on someone remembering an extra command. That obliges the seeder to stay idempotent forever — `firstOrCreate` only, no accounts, no deletes. Its `syncPermissions` on the three built-in roles is safe precisely because `RoleManager::togglePermission()` refuses to edit any of `PROTECTED_ROLE_NAMES`, so there is no user customisation there to clobber; custom roles are never touched. `PermissionCoverageTest` pins idempotency, the custom-role safety, and "creates no accounts".
  - **Sail does *not* run it automatically** (no entrypoint), so after adding a permission locally you must run `sail artisan db:seed --class=RolePermissionSeeder` yourself or the feature looks broken on your own machine. And note that the whole test suite is blind to this class of bug — `RefreshDatabase` re-seeds every test, so tests pass while the running app is missing the row. `PermissionCoverageTest` cross-checks the permissions used in `can:` route middleware against what the seeder creates, and against `RoleManager::PERMISSION_LABELS`, so a missing one fails the suite instead of surfacing as a 403 in production.

**Admin permissions are page-level, not role-level — every `/admin/*` route (and the nav bar links to it) checks a specific spatie permission, not a hardcoded role name, so custom roles created via `/admin/roles` (`App\Livewire\Admin\RoleManager`) actually work end-to-end.** `database/seeders/RolePermissionSeeder.php` seeds one permission per admin page (`users.manage`, `teachers.manage`, `classes.manage`, `students.manage`, `roles.manage`) plus the pre-existing attendance ones; `admin` gets all of them, `homeroom_teacher`/`student_rep` get none of the admin ones. `RoleManager` lets an admin create a new role, tick whichever of these permissions it should have, and assign it to an account via the existing `UserManager` role dropdown (which already reads `Role::orderBy('name')->pluck('name')` from the DB, so a new role just shows up — no code change needed there). **`admin`/`homeroom_teacher`/`student_rep` are protected**: `RoleManager::PROTECTED_ROLE_NAMES` blocks deleting any of the three (code elsewhere depends on their exact names — e.g. the `hasRole('admin')` full-access bypasses in `SchoolClassPolicy`/`AttendanceRecordPolicy`/`AttendanceQuickLink`, which are a *data-scope* concern deliberately left alone by this feature, see below) and blocks editing `admin`'s own permission set specifically (to stop an admin from accidentally locking themselves out of the whole panel by unchecking `users.manage`/`roles.manage` on their own role). A one-account-one-role assumption is unchanged — `UserManager` still assigns a single role, by design (not a scope limitation of this feature, a deliberate choice already documented on `UserManager::createUser()`).
  - **"Every class, not just `ownSchoolClasses()`" is decided in exactly one place — `User::hasAllClassAccess()` — and it is keyed off permissions, never `hasRole('admin')`.** Two permissions grant it, deliberately distinct: `classes.manage` (already means "can create/modify any class", so extending it to "can operate any class's attendance" is consistent) and `attendance.record.all` ("點名所有班級"), a pure *scope* permission carrying no management ability at all — that one exists because a 學務處 staff account needs to backfill attendance for any class while having no business touching class settings, and before it existed the only way to get school-wide attendance reach was to hand over `classes.manage` along with the whole 班級管理 page. The role-literal version of this check was a real reported bug: a custom role from `/admin/roles` given the exact same permission set as `admin` could still record attendance for *zero* classes, because it has no linked `Teacher`/`Student` row and so `ownSchoolClasses()` is always empty for it. `SchoolClassPolicy::recordAttendance()`, `AttendanceRecordPolicy::manageFollowUp()`, `AttendanceQuickLink::render()` and `attendance-quick-link.blade.php`'s "no default class → hide the link entirely" branch all call the one helper — four copies of the condition would eventually drift. **Scope and capability stay two separate checks in every one of those call sites**: `attendance.record.all` on its own grants nothing, since each site first tests the capability permission (`attendance.record` / `attendance.follow_up.manage`) and only then widens the scope. `AttendanceRecordAllPermissionTest` pins both halves, including that the new permission opens no `/admin/*` page.
  - **All three built-in roles hold `attendance.follow_up.manage` — the 學生 role (identifier `student_rep`) is no longer attendance-only.** It used to be, and `AttendanceRecordPolicy`/`FollowUpManager` both carried comments saying "副班長 can take attendance but can't write follow-ups"; that is now wrong and the comments were rewritten. What stops a student reaching another class's follow-ups is **only** the scope half of `AttendanceRecordPolicy::manageFollowUp()` (`ownSchoolClasses()->contains(...)`), so that check is now load-bearing in a way it wasn't when the permission itself also blocked them — `FollowUpManagerTest` covers both directions explicitly. Keep `FollowUpManager::boot()`'s independent `authorize()` even though every built-in role now passes the permission half: a custom role from `/admin/roles` can tick `attendance.record` without `attendance.follow_up.manage`, and `RecorderTest::test_a_role_without_the_follow_up_permission_does_not_see_the_section` pins that case down.
  - **Attendance submission is time-boxed to 07:00–17:00 for roles *without* `attendance.record.anytime`** (`App\Support\AttendanceWindow`, another plain final class for the same trait-constant reason as `AcademicPeriod`/`AttendancePeriods`/`ClassCode`). The built-in 學生 role deliberately lacks that permission; `homeroom_teacher`/`admin` hold it, because backfilling a missed session or correcting a status after a parent calls back in the evening are legitimate and must not be blocked. The gate is keyed off the permission, **not** `hasRole('student_rep')` — a custom role built at `/admin/roles` to mirror the homeroom teacher can then tick 不限時段點名 and behave identically, which the role-literal version would have silently broken (the exact shape of bug already fixed once in `SchoolClassPolicy`).
    - The restriction covers **submitting only** — the page still renders outside the window so the student can read the day's state, and so there's somewhere to *show* the explanation; a hard 403 would leave them staring at an error with no idea why. `Recorder::canSubmitNow()` is the single source both `submit()` and the Blade read, so the disabled button and the server-side rejection can't drift apart. The Blade's `@disabled` is only a hint: `submit()` re-checks and flashes an error, since a `wire:click` request can always be posted directly.
    - `AttendanceWindow::isOpen()` compares whole hours (`>= 7 && < 17`), so 16:59 works and 17:00:00 does not — deliberately avoiding a boundary that needs second-level reasoning to explain. It takes an optional `Carbon` so tests pin the clock rather than depending on when the suite runs; `AttendanceWindowTest` covers both edges. Note that **follow-ups (`attendance.follow_up.manage`) are *not* time-boxed** — only attendance submission is.
  - **The role identifier stays `student_rep` even though the UI now says 學生** — the three built-in identifiers are hardcoded in `RoleManager::PROTECTED_ROLE_NAMES` and in role-literal checks, so renaming the DB value would be a migration plus a sweep of every `hasRole`/`assignRole` call site for zero user-visible gain. Only `RoleLabel::forName()`'s mapping changed (`student_rep` → 學生). Same reasoning for the demo accounts still being named `rep1`/`rep2`.
  - **"Role" (spatie's `roles.name`, and the concept generally) is always labelled "身分" in the UI, never "角色"** — the latter reads as one more synonym for "permission" (already the word used for the individual page checkboxes) to a non-technical admin, so the two ideas need visibly different words. `App\Support\RoleLabel::forName()` maps the three built-in roles' English identifiers (`admin`/`homeroom_teacher`/`student_rep` — fixed, code depends on the exact strings, see above) to Chinese for display everywhere a role name is rendered (`UserManager`'s role dropdown and table, `RoleManager`'s table); custom roles created via `RoleManager` have no such mapping and don't need one — the create form's hint tells the admin to just type a Chinese name directly (e.g. 教務處人員), since nothing in the codebase pattern-matches a custom role's name string the way it does for the three built-ins.
  - **Every checkbox in the app (`RoleManager`'s permission matrix, the login page's "remember me") uses a shared `.field-checkbox` class that's fully hand-drawn with `appearance-none`, not the native OS checkbox.** This went through two earlier iterations before landing here: a plain `rounded border-slate-300 dark:border-slate-600` (checked state relied entirely on browser-default rendering, which is why checked-vs-unchecked was hard to tell apart, especially on `disabled` checkboxes in dark mode), then a native-checkbox-plus-`accent-color` attempt (fixed the color but the user found the accent too saturated, and it still couldn't fix `disabled` — see next point). The final, current version draws the box (`border`+`background`) and the check mark (a rotated-square `::after` border trick) entirely in author CSS, with `:checked`/`:disabled`/`:disabled:checked` each getting their own explicit `border-*`/`bg-*` pair for both themes (`dark:` variants throughout, per the theme rules above) — nothing is left to the browser to color in.
  - **Why `disabled` checkboxes specifically needed the full `appearance-none` rebuild, not just a color tweak:** browsers apply their own reduced-contrast "disabled" rendering to native checkboxes regardless of what `accent-color` is set to — a `:disabled:checked` native checkbox looks close to indistinguishable from `:disabled` unchecked, which is exactly the bug reported against `RoleManager`'s built-in-role rows (their permissions are legitimately locked via `disabled`, but that shouldn't mean "can't tell if it's on"). `appearance-none` removes the native rendering entirely, so `.field-checkbox:disabled:checked` and `.field-checkbox:disabled:not(:checked)` can be given two visibly different fill shades (`bg-slate-400` vs `bg-slate-100`, plus dark variants) with nothing overriding them.

**`UserManager`/`TeacherManager`/`SchoolClassManager`/`StudentManager` all got delete actions, and each one's delete guard exists because the underlying FK's `onDelete` behavior would otherwise be actively destructive or would 500 — never add a delete button without checking the migration's `onDelete` first.**
  - `SchoolClassManager::deleteClass()` blocks whenever the class has any `students` or any `attendanceSessions`. `school_class_student.school_class_id` is `cascadeOnDelete()` too, but that only cascades the pivot link, not the `Student` row itself (see the `school_class_student` paragraph below) — the real destructive risk left is `attendance_sessions.school_class_id`'s `cascadeOnDelete()`, which drags `attendance_records`/`attendance_follow_ups` down with it. Deleting a class with real data would silently wipe its attendance history (and detach its whole roster), not just the class row. The guard (and the corresponding "只有完全沒有學生...才能刪" comment) is there to make this only usable for "I just created this class by mistake," never for retiring an old one — old classes with real history stay forever, matching the rest of the codebase's per-academic-year-is-a-separate-row design.
  - `TeacherManager::deleteTeacher()` blocks while `homeroomClasses()->exists()`. `school_classes.homeroom_teacher_id` is `nullOnDelete()`, so nothing crashes without this guard — but a class would silently flip to "尚未指派" with no warning, which an admin could easily not notice. The guard forces reassigning/clearing the homeroom explicitly first instead.
  - `UserManager::deleteUser()` has three independent guards, checked in order: can't delete yourself (mirrors the existing `toggleActive()` self-guard), can't delete the last remaining `admin` (via `User::role('admin')->count() <= 1`, spatie's `HasRoles` scope — prevents total lockout), and can't delete an account with `hasAttendanceHistory()` (checks `attendance_sessions.recorded_by`/`attendance_records.updated_by`/`attendance_follow_ups.created_by` — none of these three FKs set an `onDelete`, so they default to DB-level `RESTRICT` and deleting such a user would 500 with an unhandled `QueryException` without this guard; the *reason* to keep the guard even if you changed the FKs to `nullOnDelete()` is that severing "who did this attendance action" from the audit trail defeats the entire point of the activitylog integration). All three guards flash a friendly `session('error')` and point the admin at "停用" instead of failing silently or crashing.
  - `StudentManager::deleteStudent()` blocks via `Student::hasAttendanceHistory()` (`attendance_records.student_id` is `cascadeOnDelete()` — the same destructive-cascade shape as `SchoolClassManager::deleteClass()`, just one level down). The button itself is hidden per-row (not just guarded server-side) whenever `attendance_records_count > 0`, eager-loaded once via `withCount('attendanceRecords')` on the whole roster rather than each row separately calling `hasAttendanceHistory()` — a class-sized N+1 (20-40 students) is cheap enough to matter for a page that renders every request, unlike the few-rows-only `SchoolClassManager`/`TeacherManager` tables where a raw per-row relationship check is fine. Critically: a student who transferred out has almost certainly already been attended at least once, so this guard *cannot* be the tool for "this student left" — see the next paragraph for the feature that actually is.
  - `UserManager::updateUser()` has the *same* last-admin guard as `deleteUser()`, checked separately — this was a real gap found and fixed, not present from the start: editing the last `admin` account's role away from `admin` (via `syncRoles()`) reaches the exact same end state as deleting them (zero literal-`admin`-role accounts left) but was going through a completely different code path with no matching check. The condition is asymmetric on purpose: it only fires when the target currently *has* the `admin` role, the incoming `$this->role` is something *other than* `admin`, and they're the *last* one — editing a non-admin, or re-confirming an admin's role as still `admin`, or editing one of several admins, are all unaffected.

**A student who transfers/graduates out is marked by creating a `StudentDeparture` row (`student_id`, `left_at`, nullable `returned_at`), never by hard-deleting the `Student` or by a single nullable column on it.** This went through one iteration first — a single `students.left_at` timestamp — before landing on a proper history table; the single-column version was confirmed to lose data the first time a student left, came back, and left again (the second `confirmMarkAsLeft()` would just overwrite the one column, silently erasing the boundary of the *first* departure, which corrupted `Recorder`/`StatusBoard`'s roster for any past date inside that forgotten gap). A student can have any number of `StudentDeparture` rows over time; `returned_at` being `null` means that particular period hasn't ended yet (equivalent to the old column being non-null), and `Student::currentDeparture()` (a `hasOne` scoped to `whereNull('returned_at')`) finds the currently-open one, if any — there should only ever be zero or one open at a time, enforced by `StudentManager` reusing (rather than duplicating) an existing open departure if `confirmMarkAsLeft()` is somehow invoked while one is already open.
  - Both marking-as-left and restoring are two-step, date-entry flows (`startMarkAsLeft()`/`confirmMarkAsLeft()` and the symmetric `startRestore()`/`confirmRestore()`, both defaulting the date `<input>` to today but freely editable, both mutually exclusive with each other and with the create/edit forms the same way `StudentManager`'s other row-level states are) — **not** immediate toggles, because an admin is very often recording a departure or a return that already happened, and every date-boundary decision downstream depends on getting that date right, not on "whenever someone got around to clicking the button." `confirmRestore()` additionally validates the return date isn't before the departure's own `left_at`.
  - `Student::isEnrolledOn(string $date)` is the single predicate answering "was this student enrolled on this date" — it walks the (eager-loaded) `departures` collection and returns false only if some departure's range strictly covers the date (`left_at < $date` and, if `returned_at` isn't null, `$date < returned_at`) — both the leave day and the return day themselves count as "still enrolled" (a departure/return is rarely a clean midnight boundary; the day it's recorded, the student may well have still been in class that morning). Callers must eager-load `departures` first or this N+1s.
  - `Recorder::students()` (the daily roster driving both the attendance form and `submit()`'s write set) applies the equivalent condition at the query level (`whereDoesntHave('departures', ...)`) rather than loading everyone and filtering in PHP, since a class roster can be 20-40 rows and there's no other reason to have them all in memory. `StatusBoard::summarize()`'s `'total'` (應到) count instead filters an already-eager-loaded `Collection` via `isEnrolledOn()` directly, since that page already loads every student in every class for the exceptions list regardless. Don't try to unify these two into one shared query-builder scope — one is a fresh query, the other is filtering an in-memory collection that's already paid for.

**`Student`↔`SchoolClass` is a plain many-to-many (`school_class_student` pivot table), not a `school_class_id` FK on `students` — a real student keeps exactly one `students` row for their entire time at the school, but is linked to a *different* `SchoolClass` row for however many semesters they've been enrolled (promotion, or a mid-semester class change, is just attaching a link to the new class; the old link is never touched).** This intentionally needs **no** date-range columns on the pivot (`started_at`/`ended_at` were considered and dropped) — every `SchoolClass` row already pins down one specific academic year/semester (see 學年制度 above), so "which class was this student in during period X" is already fully answered by *which `school_class_student` rows exist*, without needing to also ask *when*. `seat_number` lives on the pivot (`withPivot('seat_number')` on both `SchoolClass::students()` and `Student::schoolClasses()`), not on `students`, since the same student's seat number is a fact about one specific class link, not about the student globally — read it as `$student->pivot->seat_number` from a query that went through the relation (a plain `Student::find()`/route-bound model has no `pivot` populated, which is why `ClassRosterManager::startEditSeat()` re-fetches via `$this->schoolClass->students()->findOrFail(...)` before reading it, same reasoning as the "re-scope before trusting an implicit-bound model" pattern elsewhere in this file). `Student::scopeOrderBySeatNumber()` orders by the qualified `school_class_student.seat_number` column and only works when called on a query that already joins that pivot (i.e. through `SchoolClass::students()`/`Student::schoolClasses()`) — calling it on a bare `Student::query()` fails outright, there's no seat number to sort by without the join.
  - This directly fixed a latent version of the same "single mutable column loses history" bug `StudentDeparture` was built to fix, one level up: with a plain `school_class_id` column, promoting a student to next year's class would silently empty out *last* year's class roster (the very same `students()` query the old class's `Recorder` page depends on would return nothing, since every row would have already moved), making it impossible to go back and correct a stale class's attendance even though its `attendance_records` were completely untouched. The many-to-many design sidesteps this by construction: the old class's link is never mutated or removed, so its roster — and with it, `Recorder`'s ability to fix a past session — stays intact forever, for the same "past academic periods stay browsable/correctable" reason `AcademicPeriod` lets you switch back to an old year at all.
  - `student_number` is globally unique across `students` (not scoped per class) precisely *because* one real student is exactly one row for life — see the `students_student_number_unique` migration and `StudentManager::rules()`. This was a real, fixed gap: the original scoped-unique constraint let the same 學號 exist as two separate `students` rows in two different classes, which should never legitimately happen given the one-row-per-student design.
  - `class_number` is `unsignedTinyInteger`, not a string — an earlier version kept it as a string "to allow non-numeric class codes" (e.g. 忠孝仁愛-style names), but that flexibility was confirmed unused in practice (real class codes are always positive integers, e.g. Excel exports encode them as a fixed-width `grade` + zero-padded `class_number`, like `211` = 2年11班), so `SchoolClass::scopeOrderByClassCode()` no longer needs `HasNaturalStringSort`'s "sort by length, then lexically" trick — plain integer ordering is already correct. `seat_number` still needs that trick (`Student::scopeOrderBySeatNumber()`) since it stays a string.
    - **`scopeOrderByClassCode()` orders by `grade` *then* `class_number`, and that grade ordering belongs in the scope — don't add it at the call site.** It was previously named `scopeOrderByClassNumber()` and did exactly what the name said: ordered by `class_number` alone, which puts 1年1班/2年1班/3年1班 all first and only then the 2號 classes. Four call sites happened to compensate with their own `->orderBy('grade')` beforehand; the three that didn't (the 學生管理 class-filter dropdown, and both branches of `User::ownSchoolClasses()`, which feeds the nav bar's class picker) silently rendered the wrong order. A class's identity *is* grade+number — that's literally how the school's three-digit class code is composed (`App\Support\ClassCode`) — so the ordering belongs in one place. `SchoolClassTest` pins it.
  - **`App\Livewire\Admin\StudentImporter` (`/admin/students/import`) bulk-loads the school's own whole-school Excel export**, whose fixed column order is 學號/班級/座號/姓名/性別/身分證/生日 (the last two are read past and ignored — nothing in this system stores them). It is a **separate page, not a panel** on `/admin/students`, because one file spans every class in the school and the flow is three steps (upload → preview → confirm), neither of which fits inside a list page. Two behavior decisions were confirmed with the user and are the reason the code looks the way it does, so don't "simplify" either away: **(1) a row whose 學號 already exists never overwrites the stored student's name/gender** — it only adds the missing `school_class_student` link, so re-importing a stale file or a mistyped column can at worst be wasted effort, never silent corruption of correct data (the preview still *reports* a differing name so the admin isn't surprised that it wasn't applied); **(2) if any single row fails validation the entire batch is rejected** rather than partially importing, so "確認匯入" always produces exactly what the preview table showed. The error check runs again inside `import()`, not just by hiding the button — a `wire:click` request can always be sent directly.
    - The parsed/validated result lives in a **`protected` `$rowsCache`, never a public property**, and `import()` re-derives its write set from the uploaded file every request — same rule as `Recorder::$statuses` above: a public array is client-writable on every Livewire update, and a bulk importer is the last place that should trust one. The cache exists only so `render()` and `import()` don't each parse the file within one request.
    - Spreadsheets are read with **PhpSpreadsheet's `IOFactory::load()` directly, not `maatwebsite/excel`**. maatwebsite was installed first and then removed: its entire value-add here (the `ToModel`/`WithValidation`/chunked-queue import lifecycle) is unusable when the screen has to preview a whole batch before writing anything, its `Excel::toArray()` refuses a `null` import object so it needs a do-nothing marker class purely to satisfy a type, and version 4.0.2 emits `SplObjectStorage::contains()`/`attach()` deprecation warnings on this project's PHP 8.5. `IOFactory::load()` auto-detects xlsx/xls/csv on its own and returns the identical array.
    - `App\Support\ClassCode` is the single place the export's three-digit 班級代號 is decoded (first digit = grade, remaining two = zero-padded class number: `101` → 1年1班, `211` → 2年11班). It exists so no call site re-implements the `substr` and forgets the `(int)` cast that strips the padding — `"01"` would never match the integer `1` stored in `school_classes.class_number`. Anything that isn't exactly three digits with a grade of 1–3 is rejected outright rather than guessed at, since a mistyped code that silently resolves to a real-but-wrong class is far worse than an error the admin has to look at. Like `AcademicPeriod`/`AttendancePeriods` it's a plain final class, not a trait, for the same PHP trait-constant reason.
  - **Creating a student and putting them in a class are two separate admin pages, split along exactly this many-to-many boundary — not an arbitrary UI reorganization.** `App\Livewire\Admin\StudentManager` (`/admin/students`, top-level, alongside `TeacherManager`) owns the student *entity* — 學號/姓名/性別/帳號連結/轉出狀態— with **no** row-level scoping, same as `TeacherManager`/`UserManager` (anyone holding `students.manage` can touch any student in the school; there is no narrower "only my class" boundary for this page, because there's no longer a single class a student "belongs to" for that boundary to even be defined against). `App\Livewire\Admin\ClassRosterManager` (still at the original `/admin/classes/{schoolClass}/students` URL, reached via `SchoolClassManager`'s "管理學生" row action) owns *membership* — attaching an existing student to this specific class with a seat number, changing that seat number, or detaching them — mirroring how `SchoolClassManager`'s homeroom-teacher `<select>` already picks an *existing* `Teacher` rather than creating one inline (except the quick-add panel, an intentional exception documented separately). `ClassRosterManager::removeStudent()` doesn't hard-block detaching a student with attendance history in this class (unlike `StudentManager::deleteStudent()`, which does block deleting a student with any history at all) — detaching only drops the `school_class_student` row, `attendance_records` stay completely untouched either way, so there's no data-loss risk to guard against; the `wire:confirm` text just warns that correcting a past record for them in this class afterward would need re-attaching first, matching the same trade-off `CLAUDE.md` already documents for the `school_class_student` design itself just above.

**Passwords an admin sets on someone else's behalf (`UserManager::createUser()`'s initial password, `UserManager::resetPassword()`) always flip `users.must_change_password` to `true`, and `App\Http\Middleware\EnsureUserHasChangedPassword` forces the next full-page request to `/account/password` (`App\Livewire\Account\ChangePassword`) until the account holder sets their own.** This is the "force a password change after an admin-assigned password" mechanism — `must_change_password` deliberately isn't in `User`'s `#[Fillable(...)]` list (same treatment as `last_login_at`) and is only ever set via `forceFill()`, so nothing can flip it through ordinary mass assignment. Three things worth knowing if you touch this:
  - `ChangePassword::updatePassword()` requires the *current* password (re-checked via `Hash::check()`, not just "already has an authenticated session") before accepting a new one — a stolen/left-open session shouldn't be enough to lock the real owner out by itself. It deliberately does **not** call `$user->invalidateSessions()` afterward, unlike `UserManager::resetPassword()` (which does, and should — those two flows have opposite actors: reset is an admin acting on someone else's account, so nuking that account's sessions is appropriate; self-change is the account holder acting on their own session, and killing your own just-used session out from under you mid-request would be a bad user experience, not a security win, since the DB session row it would delete is the same one just successfully authenticated the current request).
  - `EnsureUserHasChangedPassword` is a plain custom middleware, so — same limitation as `EnsureAccountIsActive` (see the Livewire persistent-middleware gotcha above) — it only re-checks on a full page load, not on an already-mounted Livewire component's subsequent `wire:click`s. It must explicitly exempt `account.password` and `logout` by route name or a flagged user gets stuck in a redirect loop with no way to even sign out.
  - The nav bar's "變更密碼" link is unconditional (no `@can` guard) — every authenticated account can reach it voluntarily, not only when force-redirected there; it's the account holder's only route to changing their own password at all, since `UserManager` deliberately keeps its `resetPassword()` off-limits for self-service (see the delete-guards paragraph above's sibling behavior: `startResetPassword()`/`resetPassword()` both no-op on `$user->is($this->currentAdmin())`, steering the admin to this page instead of resetting their own password admin-side).

**A route that must show different content per role/permission (not just allow-or-403) puts that branching in a thin invokable controller, not in the Blade template.** See `App\Http\Controllers\ShowDashboardController` picking between `dashboard.status-board` and `dashboard.welcome` based on `attendance.dashboard.view` — same family as `ShowAttendanceController`/`GoToMyClassAttendanceController`. This differs from the all-or-nothing case (`/attendance/{schoolClass}`), which gates at the route-middleware level (`can:recordAttendance,schoolClass`) since there's no "everyone can visit, content varies" requirement there.

**`StatusBoard` shows all three periods side by side per class (not one at a time like `Recorder`), and collapses the four `AttendanceStatus` cases into a binary "出席/缺席" pair for that summary via `AttendanceStatus::countsAsPresent()`** (`Present`/`Late` → counts as present, `Absent`/`EarlyLeave` → counts as absent) — this grouping exists *only* for the dashboard's at-a-glance columns; `Recorder`'s per-student status dropdown still offers all four values individually, and the "需留意學生" (needs-attention) exception list only includes the absent-like two (a late student isn't something the dashboard needs to flag). Don't reuse `countsAsPresent()` logic to mean "should this show up in an audit/follow-up list elsewhere" — it's specifically the dashboard's coarse bucketing.

**`StatusBoard`'s 全螢幕 button turns the page into a table-only wall display, and the enlargement is computed at runtime rather than being a fixed CSS bump — fullscreen on its own does nothing for legibility.** `requestFullscreen()` only surrenders the browser chrome; the page still lays out at identical CSS pixels, and since the board container is capped at `max-w-5xl` it would just gain more empty margin on a large screen. Three pieces have to stay in sync or the feature quietly stops working:
  - **Fullscreen targets `document.documentElement`, never the table container.** The board polls with `wire:poll.15s`; if the fullscreen element were a node inside the component that Livewire's DOM morphing replaced, the browser would drop out of fullscreen — a visible flash every 15 seconds. "Show only the table" is therefore achieved by *hiding everything else* (`.board-chrome` on the header/date/button, plus `nav`) rather than by fullscreening the table element. Same visual result, none of the morph risk.
  - **The type size is binary-searched by `fit()` in the Blade's `x-data`, not written into the CSS.** A fixed multiplier cannot satisfy "as large as possible" *and* "never needs scrolling" at once, because how much fits depends on the class count and how long the 需留意學生 lists happen to be that day. Everything inside the table is sized in `em` so one root value scales the whole thing. A `MutationObserver` re-runs the fit when polling brings in taller content — deliberately a DOM-level observer rather than a Livewire hook, so it doesn't depend on framework-internal API names.
  - **The height chain must stay unbroken: `.status-board` → `.board-shell` → `.table-wrap`.** `flex` properties only affect *direct children* of a flex container. This broke once in exactly that way — an Alpine `x-data` wrapper was inserted between the board root and the table, so `.table-wrap`'s `flex: 1; min-height: 0` applied to nothing, its height fell back to `auto`, `scrollHeight` always equalled `clientHeight`, and the search concluded "it fits" at every size and jumped straight to the 96px ceiling (two classes visible, no way to scroll). `.board-shell` exists to carry the flex container through that layer; `min-height: 0` matters too, since a flex child's default `min-height: auto` lets it grow to its content and never report overflow. If you add another wrapper in here, extend the chain.
  - **The computed size is published as `--board-font-size` on `<html>`, never as an inline style on the table container.** That container lives inside the Livewire component, so the 15s poll's morph wipes any attribute the server didn't render — which silently dropped the table back to its unscaled `0.875rem` mid-session. `<html>` is outside Livewire's reach. The `overflow-y: auto` fallback rides on a `.board-overflow` class on `<html>` for the same reason.
  - **Measure after a real reflow, not on `$nextTick`.** `fullscreenchange` fires while the browser is still transitioning, and Alpine's `$nextTick` is a microtask that runs *before* the next layout — measuring there reads stale geometry. `schedule()` chains two `requestAnimationFrame`s; `fit()` additionally bails and reschedules if `clientHeight` is still implausibly small.
  - If even the minimum size overflows, `fit()` flips the container to `overflow-y: auto`. The container is otherwise `hidden` (no scrollbar once fitted), and silently clipping whole classes off a wall display is far worse than making it scrollable in that pathological case.
  - Note the gap this leaves: **F11 (browser-level fullscreen) does not set `document.fullscreenElement`**, so it triggers none of this. Only the in-page button does.
  - Blade-level `text-xs` utilities on the exceptions column and the 未點名 cell sit in Tailwind's utilities layer, which comes *after* components — restyling `.data-table` alone cannot override them. The fullscreen block reaches them with a deliberately more specific selector rather than `!important`.

**Printing goes through the browser (`window.print()` + an `@media print` block in `app.css`), never a server-side PDF library — and that was a deliberate rejection, not an oversight.** `App\Livewire\Attendance\MorningAbsenceList` (`/attendance/morning-absences`) is the one page built to be printed: the whole-school 上午 absence sheet the 學務處 posts up, replacing the hand-copied list described in system_structure.md's 使用場景. dompdf and friends were ruled out because **their bundled fonts contain no CJK** — every Chinese character prints as blank or tofu unless a CJK font file (megabytes, per weight) is committed and wired into the font map, and the browser already has the page rendered in the correct typeface. The browser's own print dialog also covers "I need a PDF" via Save as PDF, so the PDF library buys nothing here.
  - Three things the print stylesheet must keep doing, each fixing a specific real failure: **(1)** force white background / black text under `html.dark`, because this project's dark mode is class-based and browsers don't print background colors — a dark-theme user would otherwise get pale grey text on white paper; **(2)** `thead { display: table-header-group }` so column headers repeat on every sheet; **(3)** `break-inside: avoid` on each `<tbody>`, because each class is one `<tbody>` whose 班級 cell uses `rowspan` over its absentees — split that group across a page boundary and the continuation rows land on page 2 with no class column at all (the `rowspan` cell stayed behind on page 1).
  - The page draws **its own** title/date header (`hidden print:block`) rather than relying on the browser's print header. The browser's cannot be disabled from the page (only by the user unticking it in the print dialog), and more importantly it stamps *the moment of printing* — which is simply wrong when someone reprints yesterday's sheet, exactly the case the page's own date picker exists for.
  - 「到齊」 and 「未送出」 are both printed as explicit rows rather than omitted. A class missing from the sheet would be indistinguishable from a class with nobody absent, and spotting which class hasn't reported yet is the sheet's main job — the same `attendance_sessions`-row-exists-means-attendance-was-taken signal documented above.
  - `print:hidden` lives on the shared `<nav>` in `nav-bar.blade.php`, not on this page, since navigation is useless on paper for any page that ever gets printed.

**A tooltip/popover nested inside a horizontally-scrolling container (`.table-wrap`'s `overflow-x-auto`) gets clipped by that ancestor if positioned `absolute`** — setting `overflow-x` to anything but `visible` implicitly computes `overflow-y` as at least `auto` too per the CSS spec, so a popover meant to escape the row visually (e.g. `StatusBoard`'s per-exception follow-up hover card in `status-board.blade.php`) will get cut off. The fix used there: Alpine computes the trigger's `getBoundingClientRect()` on `mouseenter` and sets inline `left`/`top` on a `position: fixed` element — `fixed` positioning escapes ordinary overflow clipping (nothing in this layout applies a `transform` to an ancestor, which would otherwise re-scope `fixed`). `x-cloak` is used on it to avoid a flash-of-visible-content before Alpine initializes; the corresponding `[x-cloak] { display: none !important; }` rule lives in `resources/css/app.css`'s `@layer base`, not something Tailwind provides automatically.

**Database backups run as a `backup` service inside the production compose stack, not as a host cron job** — a host crontab is per-machine setup that has to be redone on migration, and forgotten manual steps have already caused two incidents here. `docker/production/backup.sh` (bind-mounted into a `mariadb:12.3` container, so no extra image and no rebuild to tweak the policy) loops until `BACKUP_HOUR`, dumps with `--single-transaction` (consistent snapshot without locking — the school is using the system all day), rotates to 30 daily + 12 monthly, and exposes `once`/`list`/`verify`/`restore` subcommands so every operation is the same on any host. Points that are load-bearing:
  - **`BACKUP_PATH` must be a host directory, never a volume declared in this compose project.** `docker compose down -v` deletes the project's volumes, which would take the backups along with the database it is meant to protect — exactly the incident that motivated this.
  - **A dump is written to `.tmp` and only renamed on success**, and is rejected if it is under `BACKUP_MIN_BYTES` or fails `gzip -t`. A truncated dump that still produced a file is the failure mode that looks fine until you try to restore it.
  - **Backups do not depend on any secret.** The dump is plain SQL and contains no DB accounts (only `attendance_system` is dumped; users live in the `mysql` system database), so it restores into an environment with entirely new passwords — verified end to end, including that users' existing login passwords still work (bcrypt hashes don't involve `APP_KEY`, and the project has no `encrypted` casts). Losing `APP_KEY` only logs everyone out. And while containers are running, the whole of `.env.production` can be recovered from `docker inspect`.
  - **The heartbeat is reconciled from the files on disk, not written once and forgotten.** `backup` has no dependency on `app` (both only wait for `mariadb`), so on a first deployment the startup backup routinely completes *before* migrations create `backup_runs` — the file lands fine but the heartbeat is lost, and the app then reports "never backed up" for up to a day on a perfectly healthy install. A monitoring signal that cries wolf on day one teaches people to ignore it, which destroys its entire value. So `sync_heartbeats()` inserts a row for every daily file that has no matching `file_name`, using **the file's own mtime** as `completed_at` (backfilling a three-day-old file must not read as healthy), and it runs both at container start and after every backup — any lost write heals itself on the next run or restart. `wait_for_table()` additionally waits up to 120s at startup so the race usually never happens in the first place. Note the script is *bind-mounted*, so fixing it needs only `git pull` + `restart backup`, no image rebuild.
  - **The bind mount is the whole `docker/production` *directory*, never the single `backup.sh` file — a single-file bind mount cannot survive `git pull`.** Git replaces a file by writing a new one and renaming over it, so the inode changes; a file bind mount is pinned to the inode captured at container-create time. The running container keeps serving the *old* content, and `docker restart` then fails outright with `failed to create shim task ... no such file or directory`, forcing a full `up -d --build`. Verified by direct experiment (file mount: stale then unrestartable; directory mount: picks up the new content and restarts cleanly). Because of this the script lives at `/scripts/backup.sh` inside the container rather than on `PATH` — the container runs as a non-root user and so cannot symlink it into `/usr/local/bin`.
  - **Staleness is surfaced in the app, not left to someone remembering to check.** Each successful run inserts a heartbeat into `backup_runs`; `App\Support\BackupStatus` + `<x-backup-warning>` (in the shared layout, gated on `audit.view`) warn after `backup.warn_after_hours`. Using a DB heartbeat rather than reading the backup directory keeps the app completely decoupled from where backups live — `BACKUP_PATH` changes when the host changes. The heartbeat proves the job completed; `backup.sh verify` separately proves the files still exist. Default `monitor_enabled` is false so Sail doesn't warn on every page.
  - **The off-site mirror lives inside `backup.sh` too — it used to be a separate host script plus a cron entry, and collapsing it back in was the right call once production moved off WSL.** The host-script design existed for WSL-specific reasons: the target was a disk mounted with `wsl --mount` under `/mnt/wsl` (which is itself tmpfs), the mount could vanish on any WSL restart, `cron` does not auto-start there, and a docker bind mount resolves once at container-create time. On a real Ubuntu server the second disk is in `/etc/fstab` and simply stays mounted, so all of that evaporated — `mirror-backups.sh` and its `init`/`install`/`status` subcommands were deleted, and `mirror_sync()` now runs at the end of every successful backup (plus once at container start, so a disk that was remounted catches up without anyone remembering to trigger it). One script, one schedule, one identity writing every file — which also removed a real bug: `.last-mirror` was being written by whichever user ran the host script, so a single `sudo` run left it root-owned and every later cron run failed to update it while the copy itself succeeded, making `verify` cry "mirror is stale" about a mirror that was working.
    - **The `.attendance-mirror-target` sentinel is the load-bearing check, not the directory's existence.** With the disk unmounted, the mount point is an ordinary empty directory *on the system disk* — copying there looks completely normal and silently lands the "off-site" copy next to the original. The sentinel lives on the disk itself, so no mount means no sentinel means no sync. The second check is that source and target are on different devices (`stat -c %d`). A failed mirror never fails the backup: the local file is the primary goal, and `mirror_sync || true` keeps it that way.
    - **Copy-what's-missing instead of rsync.** Backup files are immutable once written (daily names carry a timestamp, the monthly file is created only on the month's first run), so a plain loop over "files the target doesn't have" is exactly equivalent to a delta sync — and the `mariadb` image ships no rsync, so this avoids installing one. Copies use the same `.tmp`-then-rename discipline as the dump itself.
    - **Nothing is ever deleted on the mirror side, deliberately.** Propagating deletions would carry both ordinary rotation *and* someone wiping the source straight through to the copy — turning the exact scenario backups exist to survive into a certainty. Growth is released only by an explicit `backup.sh mirror-prune <days>`.
    - Because a compose `volumes:` entry cannot be conditional, the mirror mount falls back to `/tmp` when `BACKUP_MIRROR_PATH` is unset; what actually switches the feature on is `BACKUP_MIRROR: '${BACKUP_MIRROR_PATH:+/mirror}'`, which stays an empty string in that case so the script skips the whole section and never touches the placeholder mount.

**Production deployment is a separate, minimal Docker setup behind `cloudflared`** — `compose.production.yaml` + `docker/production/{Dockerfile,nginx.conf,php.ini,php-fpm.conf,entrypoint.sh}`, sharing nothing with Sail's dev-only `compose.yaml`. Operator-facing steps (build from scratch, day-to-day, updates, troubleshooting) live in [DEPLOYMENT.md](DEPLOYMENT.md); design rationale is in system_structure.md's 生產環境部署. The things most likely to bite a future change:
  - **Nothing publishes a port to the host.** The only inbound path is cloudflared's outbound tunnel. This is what makes `bootstrap/app.php`'s `trustProxies(at: '*')` safe — don't add a `ports:` mapping without re-reading that reasoning.
  - **The client IP arrives via `CF-Connecting-IP` → nginx `real_ip` → `REMOTE_ADDR`, and `X-Forwarded-For` is deliberately *not* trusted.** Cloudflare *appends* to `X-Forwarded-For` rather than replacing it, so a visitor who sends their own `X-Forwarded-For: 1.2.3.4` reaches the app as `1.2.3.4, <real ip>` — and Symfony, with every proxy trusted, takes the leftmost entry. Verified: `request->ip()` returned the forged value. That makes the audit log's login IP forgeable, which defeats the entire point of recording it. `CF-Connecting-IP` is always overwritten by Cloudflare and cannot be spoofed, so nginx resolves it into `$remote_addr` (`set_real_ip_from` the RFC1918 ranges — the only things that can reach nginx are containers) and `trustProxies()` omits `HEADER_X_FORWARDED_FOR` so Laravel just uses `REMOTE_ADDR`. `TrustedProxiesTest` pins both directions. Without the nginx half, every log line shows the cloudflared container's address.
  - **php-fpm's access-log `%R` is the FastCGI *peer*, not the client** — it always prints nginx's container address, so `docker/production/php-fpm.conf` overrides `access.format` to use `%{REMOTE_ADDR}e` (the FastCGI param, which `real_ip` has already rewritten to the true client). Verified side by side in a standalone pair: `%R` gave the nginx container IP while `%{REMOTE_ADDR}e` gave the forwarded client. A field that always shows the same value is worse than no field — it reads as information and misleads. The format also carries request duration and peak memory, which nginx's own log cannot provide, so the second access log earns its place instead of duplicating the first.
  - **`add_header` in nginx is not additive across levels — a `location` that declares *any* `add_header` inherits *none* from the server block.** The `/build/` location sets `Cache-Control`, which silently dropped all four security headers (including `X-Content-Type-Options`) from every CSS/JS response until they were repeated inside it. Anywhere a new `location` adds a header, the whole set has to be repeated.
  - **Crawler exclusion is done in the app/nginx, not in the Cloudflare dashboard**, so it travels with the deployment and can't be undone by someone editing dashboard settings: `public/robots.txt` says `Disallow: /` and nginx sends `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet`. Both are needed and they do different jobs — robots.txt stops *crawling*, `X-Robots-Tag` stops *indexing*. A URL blocked only by robots.txt can still be listed (bare, without content) if something links to it, and because crawling is blocked the crawler never sees the `noindex`.
  - **`bootstrap/app.php` now configures `trustProxies()`/`trustHosts()`, and both are load-bearing.** Without trusted proxies `$request->ip()` becomes the nginx container's fixed internal IP, which collapses `LoginController::throttleKey()` (`username|ip`) into one bucket for the whole school — anyone failing 5 logins locks that account out from *everywhere*, and it's the app's only brute-force defense. `isSecure()` also goes false, dropping the session cookie's secure flag and generating `http://` URLs. `tests/Feature/TrustedProxiesTest.php` pins all of it. `trustHosts()` must pass `at:` explicitly — `trustHosts(subdomains: false)` alone silently does nothing, because `TrustHosts::hosts()` ignores the `subdomains` flag when `$alwaysTrust` is null and just returns the "APP_URL and all its subdomains" regex.
  - **`DatabaseSeeder`'s `admin` account is now inside the `local`/`testing` guard**, alongside `DemoDataSeeder`. It used to be outside it, which meant a production `db:seed` created a full admin with the hardcoded `UserFactory` password `password`. Production creates the first admin with `php artisan admin:create` (`App\Console\Commands\CreateAdminUser`) instead — password entered interactively, never as a CLI option (that would land in shell history and `ps`), and `must_change_password` set so the holder replaces it. Don't move any known-password account back outside that guard.
  - **The app's own files are read-only to PHP in production.** The runtime stage copies them *without* `--chown`, so they stay root-owned while php-fpm runs as `www-data`; only `storage/` and `bootstrap/cache/` are writable. A feature that writes anywhere else in the project works under Sail and fails in production. `storage/` also has no volume, so it is wiped on every container rebuild — fine today (logs go to stderr, uploads are Livewire temp files only), but a "keep the uploaded file" feature would need a volume added.
  - **`config:cache` runs in the entrypoint**, so `env()` outside `config/*.php` returns null in production. Also: editing `.env.production` and running `docker compose restart` does *nothing* — restart reuses the existing container with its baked-in environment; only `up -d` recreates it.
  - **Assets are compiled in the image's `assets` stage, which only copies `resources/`.** Tailwind v4 decides what to emit by scanning source; there are currently no CSS class strings under `app/` (verified), so if a Livewire component ever builds class names in PHP, those utilities silently won't exist in production CSS until `app/` is added to that stage.
  - **`compose.production.yaml`'s `name:` must stay, and it cuts both ways.** Without it compose derives the project name from the directory, colliding with Sail's — running the production compose on a dev machine then recreates Sail's `mariadb` container with production settings and breaks the dev environment (hit for real). But because the name is *fixed*, **every invocation of that file on a given host targets the same containers and the same database volume no matter which directory it runs from** — compose identifies a project by name, not by path. That destroyed a running stack for real: a smoke test run from the dev checkout (`up -d --build`, then `down -v`) was actually operating on the live stack deployed from `/opt`, and the `-v` deleted its database volume outright — accounts, classes, students, attendance records and the audit log, with no backup. **Never run `compose.production.yaml` on a machine that already hosts a stack from it.** If a smoke test genuinely has to happen there, give it a throwaway project name (`docker compose -p attendance-smoke-test ...`, which outranks the file's `name:`) and clean up with the same `-p`. Treat `down -v` as "I am deliberately erasing the database" — there is no confirmation and no undo.
  - Alpine's `/bin/sh` is busybox ash with **no brace expansion** — `mkdir -p a/{b,c}` silently creates a directory literally named `{b,c}` and the build still succeeds (hit for real; the Laravel storage skeleton went missing). Likewise, php-fpm's `error_log` is a *global* directive and makes fpm refuse to start if placed in the `[www]` pool block.
